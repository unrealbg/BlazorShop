# Public SSR catalog and search

## Implementation and compatibility

Issue [#126](https://github.com/unrealbg/BlazorShop/issues/126) adds public discovery to the existing .NET 10 static SSR Storefront. The implementation starts from `134609959c22e2b87fe1348a633ceddd9c84ff9c` and follows the [search/catalog recommendation](../listing-pages/search-catalog-recommendation.md). Native GET forms and links call the existing published catalog API through `StorefrontApiClient`; the page reuses `ProductCatalogQuery`, `PagedResult`, `ProductGrid` and `ProductCard`. Search matches the existing API's product name/description behavior.

The WebAssembly `/search-result/{Filter}?sort=...&category=...` route, its callers, modal/product behavior and client URL resolver are unchanged. Public product/category slug links, variant purchase navigation, cart storage and anonymous/authenticated checkout handoffs remain in their existing applications. No interactive render mode, token issuance, authorization mechanism, business endpoint or schema is introduced.

## Public URL and indexing policy

The new public route is `/catalog`. Its supported query parameters are:

| Parameter | Behavior |
| --- | --- |
| `q` | Trimmed product search term; blank means all products. The new UI accepts up to 200 characters. Longer terms return a recoverable 404 without issuing a catalog product query. The API contract is unchanged. |
| `category` | One published category GUID from the existing categories endpoint. Missing/blank means all categories. Malformed, empty-GUID and unknown/unpublished categories return the same 404 presentation. |
| `sort` | `newest` (default), `oldest`, `price-low-to-high`, `price-high-to-low`, `name-ascending`, `name-descending`. Unknown values reset to newest with a visible notice. Existing API tie-breaking is preserved. |
| `page` | Positive, invariant decimal page number; 24 products per page. Missing/blank is page one; zero, negative and nonnumeric values reset to one with a notice. Positive integer overflow and pages beyond the safe API offset bound return 404. A valid page beyond the actual last page also returns 404. An empty result on page one is a healthy 200. |

Forms intentionally omit `page`, so changing the term, category or sort starts at page one. Pagination preserves all normalized filters, uses real total counts and provides first/last, nearby, previous/next links as appropriate. Default/empty parameters are omitted from canonical/pagination URLs; GUIDs, sort names, encoding and page numbers are normalized. Extra unsupported query parameters have no effect.

All new catalog URLs initially emit **`noindex,follow`** in both HTML metadata and `X-Robots-Tag`, and are excluded from the autogenerated sitemap. Enabling indexing of the unfiltered first page requires a separate owner decision after canonical/pagination review. Healthy pages have a self canonical preserving distinct terms, categories, sorts and page numbers; later pages are not collapsed onto page one. Search terms are HTML-encoded and are not interpolated into titles, descriptions or structured data. No catalog JSON-LD is added. Existing product/category SEO remains unchanged.

Healthy catalog responses use `Cache-Control: private, no-store`, including anonymous searches. This conservative policy avoids shared caching of queries or session-dependent shell content. API failures and inconsistent paging payloads produce 503/no-store/noindex,nofollow with a retry link, rather than a misleading empty result. Unavailable and 404 pages suppress canonical/success metadata. Catalog requests use the unchanged isolated API HttpClient and read-only layout session observation; no refresh rotation is added.

## Visual adaptation and evidence

The reference pages are `catalog.html`, `search-results.html` and the shared UI v2 component/style specifications. The catalog uses a bordered desktop sidebar and product grid; keyword results use the horizontal filter panel. Both stack controls on narrow screens. The existing shell gains a real search form and Catalog links in desktop/mobile/footer navigation.

Intentional differences from the mockups:

- Category is a single select because the existing query supports one category. Only the six real sorts are offered. Stock, sale, price-range, size, ratings, Wishlist and suggestion controls are omitted because there is no supported corresponding catalog contract.
- Existing product cards and real API images/prices replace prototype records, drawings and invented commerce labels. The sidebar catalog uses three columns on wide screens to retain readable existing card actions; full-width search uses four. Both use two columns at tablet/mobile widths. Missing images retain the shared fallback.
- Native labels, visible focus rings, 44 px controls, result counts, empty/retry/reset states and pagination replace static mockup behavior. Filters remain visible without JavaScript, rather than requiring a client-side drawer.
- The existing account/cart shell and footer are retained. Prototype-only footer capabilities and static totals are not introduced.

Baseline captures of the unchanged New Releases listing at 320/390/768/1440 px were produced with the existing Playwright listing test before the implementation. There was no public catalog/search page in that baseline. Selected baseline images are stored in `baseline/`. Final-head CI browser artifacts contain `ui-v2-catalog-search/` with `catalog-*`, `search-results-*`, `empty-*`, `last-page-*` and matching `prototype-*` captures at all four widths. These are screenshots of the running Storefront with disposable, synthetic database records; the image sample loads a real repository WebP asset. They are not production merchant-data validation.

## Remaining limits

- Public first-page indexing approval and migration of WebAssembly search callers are separate decisions. This implementation deliberately preserves both discovery entry points.
- Search, category and sort capabilities remain those of the existing API; no full-text engine, multi-category query, price/stock facets or new rate-limit policy is added.
- Count and items are separate existing API reads. A concurrent publication change can yield inconsistent metadata; this page fails safely with a retryable 503 rather than presenting an incorrect result count. Snapshot/query contract changes are outside this slice.
- Native SSR discovery works without JavaScript; existing cart actions still require their existing JavaScript behavior. This PR does not create a new no-script commerce contract.
- Catalog visual/a11y checks cover Chromium, four viewports and keyboard use. They are not a screen-reader, exhaustive accessibility or catalog cross-browser certification. The separate Firefox/WebKit security suite does not certify these layouts.
- No production, live payment/email, proxy attribution, unified routing or infrastructure validation is performed. Existing release limitations and security contracts remain in force; this is not deployment approval.

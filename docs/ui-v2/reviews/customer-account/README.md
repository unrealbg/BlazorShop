# UI v2 — Customer account and authentication

Based on `master` at `48c7bda62e30e692d7812ef18dc27b03ae034054`, including demo JWT/session isolation from PR #118.

## Presentation

The existing WebAssembly login, registration, email confirmation, account overview, orders/detail, profile, notifications, settings and workspace entry use the corresponding `docs/ui-v2` prototypes. The access layout supplies the light brand header, centered login panel, registration form with an account-benefits sidebar and explicit confirmation states. The account layout supplies the light header and persistent account navigation, stacking above content on smaller screens.

The scoped `ui-v2-account.css` adapts the prototype colors, typography, spacing, panels, blue actions, badges and form controls. It does not import prototype scripts or global selectors into other workspaces. Order detail retains the real table and switches to labeled rows on narrow screens. Form labels, autocomplete hints, linked validation messages, status/alert regions, skip links and visible keyboard focus improve access.

Unsupported remember-me, password-reset, wishlist, timeline, support and notification-preference controls are omitted. Overview retains the real profile, recent orders and inbox instead of inventing totals or active-order statistics. The existing API does not supply all prototype delivery/timeline details. Notifications remain the existing in-memory inbox and are marked read on entry; no persistence is added.

## Compatibility

Authentication component code-behind, account operation handlers, `EditForm`, DataAnnotations, validation messages, submission gates, API requests, notification subscriptions and session refresh are preserved. Login keeps both routes, including the checkout continuation path. Account authorization imports and `AuthorizeRouteView` remain unchanged. Order statuses and financial snapshots come from the existing API; payment, checkout and inventory operations are unmodified.

`DemoTokenValidation`, `DemoSessionMiddleware`, bearer configuration, demo lifecycle, role policies, redirect resolver, refresh-token/logout cleanup, Domain, Application, schema and production configuration are unchanged. Demo actions remain available in an expandable section of the sign-in form.

The private HttpClient also uses the existing `BrowserCredentialsHandler`, inside the unchanged `RefreshTokenHandler`. This restores delivery of the existing session cookie on permitted cross-origin API calls, including a retry after refresh. No origins, CORS policy, cookie attributes, tokens or server validation rules change. The browser fixture uses HTTPS on the same hostname with different ports: cross-origin and same-site. Its regression verifies the existing Secure/HttpOnly/SameSite=Lax cookie on both private attempts, a successful real refresh and a successful retried API response. A controlled first-response 401 triggers the existing retry path. This does not claim support for unrelated cross-site hosting.

## Verification

The seven existing mandatory Playwright scenarios remain. Four additional mandatory scenarios exercise access forms/registration/confirmation, account operations and responsive orders, loading/empty/error/retry states, and customer/admin/demo login/refresh/logout/session isolation. The strict TRX verifier requires all eleven, passing in both consecutive suite runs.

The browser fixture creates synthetic accounts and order snapshots in the isolated test database. Test-only demo mode is enabled; email delivery is disabled. Registration submits to the real API. Confirmation failure uses the real API; deterministic loading/success presentation uses a browser-intercepted response, not a production endpoint or fake application data. Existing backend tests remain responsible for Identity token validity. Error/loading orders use a controlled network interruption and then recover through the real Retry action.

Screenshots from the running application are recorded under `ui-v2-account/` in each browser artifact at 320, 390, 768 and 1440 px. The checks cover document overflow, clipped panels/inputs/tables and keyboard skip/focus behavior. Additional captures show confirmation and order states and a real in-app notification generated by password change. Access-page local screenshots are supplemental; authenticated/database/browser evidence must come from full CI.

Local Release restore/build and the non-container suite passed (733 tests; 10 existing live smoke skips). The final PR description records the exact validated SHA, CI/Code Analysis links, audit artifacts, container/Compose/published-assets results, both strict browser results and screenshot evidence. Earlier-head runs are not final-head evidence.

## Review limits

No deployed environment, real customer, payment or email delivery is exercised. Browser coverage is Chromium. The new security browser scenario complements the 34 unchanged HTTP isolation cases from PR #118; it does not replace them. Readiness requires successful final-head validation and visual inspection of the authenticated screenshots.
